## 4. 两侧内部接线约定

这些是工程内部职责约定，函数名和类组织可以采用等价的简单实现。跨 A/B 的公开方法和数据结构仍严格使用现有合同。

| 接线点 | 数据与行为 |
| --- | --- |
| A1 → A2 发射 | A1 分配唯一 `shotId`，提供当前玩家、球类、固定起点与已锁定的 `aimDeg/power01`；A2 同步创建本次球，不能读手套坐标或自行扣库存 |
| A2 → A1 投掷结束 | 所有球与效果稳定后，回报本次 `shotId` 和场景快照：球 id、归属、球类、位置、半径、是否在场；同一投只回报一次 |
| A1 → A3 视图 | 游戏只读状态包含模式、当前玩家、库存、阶段、可见预览、锁定值与结果；发射起点由游戏保存供预览和发射共同读取 |
| A4 → A1 模式规则 | 以纯数据/纯函数提供初始库存、关卡、下一玩家与结束/计分规则；不拥有第二套回合计时器或物理世界 |
| B1 → B2 观测 | 只交付通过身份、配置、帧序号与时效校验的原始候选及采样时间；不可用到达时间刷新旧帧 |
| B2 → B3 手套状态 | 有效性/失效原因、玩家档案版本、校准映射后的角度/力度、内部距离比、手势所需中点、rearmed 与原采样时间 |
| B3 ↔ A1 | `createMotionController` 与 `MotionHost`；通过 setContext、report、submit 连接，B 不导入 Phaser、不推进游戏阶段 |

为保证“发射只发生一次”，A1/A2 接线采用同步建球与提交：建球成功才扣库存并发布 resolving；失败回滚本次新对象并保留原状态。内部建球异常由 A 记录诊断，不能返回 accepted=true；调用方捕获异常，禁止自动重发新 commandId。无需为此擅自扩展公共错误枚举。

本轮不建立通用插件系统、网络消息层或通用 ECS。模拟端和调试页仅服务开发，不能作为生产接线的替代品。

## 5. 公共验收规则

所有卡片均须区分三种证据：

1. **自动验证**：纯规则、状态、时序与固定样例；可以用假的时钟和可控输入。
2. **浏览器验证**：真实 Phaser/Worker、键盘、界面、权限与生命周期；按表操作并记录，不以 TypeScript 通过代替。
3. **真人验证**：真实手套、光照、身体动作、玩家轮换和现场性能；未观察到即标“待人工确认”。

已有 `fixtures.json` 是输入和预期结果，不是测试执行记录。已有自动测试只有七个计分样例；各任务需要接入自己负责的样例，不得把 fixtures 全部写成已通过。

开始前执行 `npm.cmd run doctor` 和 `npm.cmd run check:vendor`。各卡中的定向测试命令是**交付后的验证入口**，相应测试文件需由该卡创建。检查修改涉及的部分；合入可运行版本前完成：

```powershell
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
```

Windows 用 `npm.cmd`，其他系统用 `npm`。构建通过后按任务检查 preview 页面；dev 能运行不等于构建版已验证。界面布局等简单改动以浏览器检查为主，测试集中在规则、状态及失效边界。

## 6. 完成定义与记录

每张任务卡的完成条件：

- 约定的模块和调试入口已存在，可按说明复现。
- 必需验收逐项有实际结果；失败项已解决，无法真人验证的项目明确保留待确认。
- 新增资源可释放；退出、重开、切换与异常恢复没有旧命令或重复监听。
- 共享文件变更已同步；没有凭空新增协议字段或把参数写成多份常量。
- 使用 [验收记录模板](验收记录模板.md) 留下版本、命令、证据与限制。

“开发完成但真人验收待确认”和“全部验收完成”分别记录。B3 的可选确认动作单列状态；默认动作完成不会自动代表可选动作通过。
